## Apple 平台线（apple-platform）


### 角度：foundation-models

**小结**：For this product's actual need — LOCAL on-device summarization/labeling of agent actions, never autonomous decisions — the Apple Foundation Models framework is BROADLY AVAILABLE TODAY, not a "first batch." The on-device model has shipped to third-party apps since macOS 26 (Tahoe)/iOS 26 in fall 2025: it is free, runs entirely on-device/offline, and requires NO Apple approval, waitlist, or entitlement for basic SystemLanguageModel use — only that Apple Intelligence is enabled on a compatible (Apple-silicon) Mac. The user would NOT be in any "first batch"; they would be adopting a year-old, generally-available API. The API surface fits the use case well: LanguageModelSession, guided generation via @Generable / @Guide for typed structured output (ideal for labeling agent actions into enum/struct schemas), tool calling, and streaming. The realistic limits matter: a ~3B-parameter, 2-bit-quantized model with only a 4,096-token context window, explicitly NOT designed for general world knowledge or chatbot use but explicitly good at summarization/entity-extraction/classification/short-dialog — which is precisely the local labeling task here. WWDC 2026 (this week) added a larger optional on-device tier, vision input, a LanguageModel protocol to plug in Claude/Gemini, an `fm` CLI + Python SDK, and a FREE Private Cloud Compute tier — but that free PCC tier is gated to App Store Small Business Program members with <2M downloads PLUS a PCC entitlement, so a Developer-ID (non-App-Store) defensive utility almost certainly CANNOT get free PCC and should rely on the on-device model. That on-device path has no such gate and is the correct architecture for a privacy-first consent gateway anyway. The one genuine open question is whether the brand-new 2026 on-device APIs are fully usable from a Developer-ID-signed, non-App-Store binary on day one; the legacy 2025 on-device API demonstrably has no App-Store requirement.

### 角度：isolation

**小结**：For "agent works in an isolated copy, user approves a diff, we apply it to real folders" on macOS in mid-2026, the realistic ranking is: (1) git/copy-based shadow staging on the real APFS volume is the only fully-userspace, no-entitlement, no-special-OS option and is the pragmatic default for a shippable third-party app; (2) Apple's container/Containerization (now 1.0.0, June 9 2026; macOS 26+, Apple silicon) plus the new WWDC26 "container machine" with auto-shared host directories is a genuine, Apple-blessed isolation primitive a third-party Swift app CAN embed as a library — but it isolates a LINUX VM, so file edits land in a shared host folder via virtiofs, not arbitrary protected user folders, and it forces a Linux-only execution model. Virtualization.framework (full Linux/macOS VMs with VZVirtioFileSystemDevice directory sharing) is the heavyweight cousin of the same idea. App Sandbox does NOT help isolate other agents — it only confines OUR own app process. APFS snapshots are effectively closed to third parties: snapshot CREATE needs a restricted entitlement Apple grants almost exclusively to backup vendors, and revert is private. sandbox-exec still works on macOS 26.3 but is deprecated with no documented replacement for headless/CLI process sandboxing. Key correction vs. naive assumptions: containerization isolates a Linux VM (not your macOS file tree), and you cannot snapshot-rollback a user's folder without Apple's blessing — so the "copy + diff + apply" pattern is best built on plain filesystem/git staging, optionally hardened by running the agent's tools inside a container machine.

### 角度：touchid-se

**小结**：For a Developer-ID-signed (non-App-Store) menubar macOS app acting as a consent gateway, Touch ID + Secure Enclave is a sound foundation for per-action approval as of June 2026 (macOS 27). LocalAuthentication's LAContext.evaluatePolicy presents Touch ID prompts from any normal GUI app (a menubar/LSUIElement agent qualifies; a pure launchd daemon does not, because LA must run in a user login/GUI context). The strongest design is a Secure Enclave-resident P-256 signing key whose SecAccessControl is created with [.privateKeyUsage, .biometryCurrentSet] (biometry-only, no passcode fallback, auto-invalidated on any biometric enrollment change) or .userPresence (biometry-or-passcode); each signature then requires a fresh biometric gesture and the private key never leaves the SE. Honest limit: the SE signs bytes and cannot attest WHAT the user saw — the app MUST hash the exact approval-UI content (action description, target, params) and include that hash in the signed payload; nothing in the OS verifies screen content for you. The one genuinely new 2026 capability: WWDC26 Session 201 announced App Attest is now supported on macOS 27, and on macOS the attestation leaf certificate now carries an "ACL Blob OID" encoding the SE access-control conditions enforced for the key — so a server can cryptographically confirm a key was biometry-gated, app-bound, and required full-security/SIP. Using the SE/keychain (not bare LAContext) requires the com.apple.application-identifier entitlement authorized by a provisioning profile, which works for notarized Developer ID apps outside the App Store; LAContext.evaluatePolicy alone needs no special entitlement.

### 角度：visibility-paths

**小结**：The collaborative (opt-in) path for giving users visibility into their own agents is real, proven, and Apple-permission-free as of June 2026. MCP is now a multi-vendor open standard (LF Projects governance, OpenAI first-party SDK support, current spec 2025-11-25 with a major 2026-07-28 release finalizing July 2026), and its own spec mandates user-consent principles that it explicitly cannot enforce at the protocol level — that enforcement gap is precisely the product's job. Multiple open-source MCP gateways/approval proxies already exist (mcp-guardian, Lasso mcp-gateway, IBM ContextForge), all running as plain user-space processes wired in via the host's MCP config: no entitlement, no TCC, no system extension. The CLI-wrapper path is equally validated by Anthropic's own open-source sandbox-runtime (Seatbelt profiles + HTTP/SOCKS5 allowlist proxies), with honestly documented limits (domain-level filtering only, domain-fronting bypass). The OS-level paths are gated exactly as expected: Endpoint Security needs a restricted, apply-to-Apple entitlement with unpublished criteria (implausible for a small consumer app, and unnecessary for a consent-based product); Network Extension content filters are self-service entitlement-wise but require system-extension + filter user approval; Accessibility observation requires an explicit per-app TCC grant and would be covert-adjacent — ruled out by principle. Meanwhile WWDC26 (this week) shows Apple converging on the same philosophy at the OS level: macOS 27 / App Intents now ship risk-based contextual confirmations and authentication policies for agentic actions, and Apple has been building MCP support into App Intents since the 26.1 betas — validation of the consent-gateway thesis, and the main commoditization risk to watch.

## Agent 生态线（agent-ecosystem）


### 角度：openclaw-overview

**小结**：OpenClaw (June 2026) is a real, MIT-licensed, self-hosted "personal AI assistant" created by Peter Steinberger that went through a rapid rename chain (Warelay → CLAWDIS → Clawdbot → Moltbot → OpenClaw, the Moltbot→OpenClaw step driven by an Anthropic trademark complaint over "Clawd"). Architecturally it splits into (a) a local-first **Gateway** control plane that brokers chat channels (WhatsApp/Telegram/Discord/Slack/Signal/iMessage + many more), tools, sessions and events, and (b) an embedded coding agent **Pi** (by Mario Zechner) whose core toolset is just Read/Write/Edit/Bash — OpenClaw swaps Bash for a sandboxable exec and layers on messaging/browser/canvas/cron/MCP tools. Users extend it via a portable SKILL.md skill format distributed through the **ClawHub** registry, and configure tools/MCP via `~/.openclaw/openclaw.json`. CRITICAL for a defensive product: OpenClaw's OWN docs state it is a single-trusted-operator model that by default runs host exec WITHOUT approval prompts (security="full", ask="off"), is explicitly NOT a hostile-multi-tenant boundary, and grants the agent broad host access (shell, files, credentials). This is exactly the surface a voluntary consent/visibility gateway would wrap — and it means a voluntary gateway sees only what an MCP/CLI-joined agent chooses to route through it, NOT the agent's direct Bash/file/exec actions, which bypass any such gateway entirely. Star/adoption numbers vary by source and date and are reported as a trajectory; several are estimates and marked as such.

### 角度：gateway-openclaw-hermes

**小结**：As of June 2026, BOTH OpenClaw and Hermes Agent can voluntarily call a third-party MCP server as a tool source, so a consent/approval gateway can plug in without forking either agent — but with very different depth. OpenClaw (docs.openclaw.ai) has an MCP client registry (`mcp.servers`, `openclaw mcp add`, stdio/HTTP) whose tools are exposed during embedded agent turns under the `bundle-mcp` plugin id; this is RECENT (a Feb 2026 issue confirms there was no native MCP client then), and the docs are clearest for bundle-contributed servers. OpenClaw additionally offers two stronger first-party gate points a gateway product can use: (a) tool policy (`tools.allow`/`tools.deny`, profiles, per-sender rules) that can disable every built-in group, and (b) the plugin hook `before_tool_call`, a documented in-process policy gate that can rewrite/block/require-approval for ALL tool kinds including exec, message, browser and MCP tools — plus a native exec-approval system (`tools.exec.mode`, /approve in chat, macOS companion app). Hermes Agent (NousResearch, released Feb 2026) supports MCP natively in its core loop (`mcp_servers` in ~/.hermes/config.yaml, stdio + HTTP/OAuth, per-server include/exclude, each server becomes an `mcp-<server>` toolset) and lets you disable built-in toolsets/tools (`--toolsets`, `/tools disable`), but its approval system gates ONLY dangerous shell commands (manual/smart/off) — file writes, browser actions, and `send_message` (WhatsApp/Telegram/Discord/Slack/Signal/Email replies) are not approval-gated, per-tool approval policies and pluggable approval hooks are still open feature requests. HONEST BOUNDARY for both: a pure MCP gateway sees nothing from built-in tools (shell/process, browser automation suites, filesystem read/write/edit, channel messaging, skills, cron, code-execution sandboxes, Hermes computer_use) unless those built-ins are explicitly denied via tool policy/toolsets — coverage is config-dependent and revocable by whoever edits config. Wrapper/second paths are documented first-party: OpenClaw Docker/SSH sandbox backends move exec+fs into containers; Hermes has six terminal backends (local/docker/ssh/modal/daytona/singularity) that redirect where shell commands execute, plus whole-agent Docker deployment. Precedent exists on OpenClaw (knostic/openclaw-shield plugin built on before_tool_call; several commercial "firewall" products) and natively in Hermes (Slack/Telegram approval buttons); third-party interception precedent on Hermes is absent because there is no hook surface yet.

### 角度：gateway-claude-codex

**小结**：Claude Code and Codex as governable targets for a voluntary, local consent/approval gateway (verified against official docs fetched 2026-06-11; Claude Code docs reference v2.1.162, Codex CLI 0.139.0 dated 2026-06-09).

CLAUDE CODE — gateway-ability grade: A- (strongly governable locally). Its hooks system is a true pre-execution choke point: PreToolUse hooks fire for every local tool call — built-in Bash/Edit/Write/WebFetch/WebSearch and all MCP tools — and can return allow/deny/ask/defer plus rewrite the tool's input (updatedInput) before execution. A gateway can attach as a command hook, an HTTP hook (localhost endpoint), or an MCP-tool hook; PermissionRequest hooks can additionally intercept the permission dialog itself. Layered under that: permissions.allow/deny/ask rules, permission modes, an OS-enforced Bash sandbox (Seatbelt/bubblewrap) with a domain-allowlist network proxy, and macOS managed-settings that can make all of it tamper-resistant (allowManagedHooksOnly, allowManagedPermissionRulesOnly, allowedMcpServers). Honest boundary list: (1) cloud sessions at claude.ai/code run on Anthropic-managed VMs where user-level ~/.claude hooks/settings do NOT carry over — only repo-committed hooks run there, so a per-machine gateway is blind to them; even with network "None" the VM still talks to the Anthropic API; (2) the agent's own model-API traffic is not a tool call and is never hook-visible; (3) without MDM-managed settings the gateway is purely voluntary — the user (or the user's settings edits) can disable hooks (disableAllHooks) and the file watcher picks up hook-config edits automatically; (4) the sandbox proxy filters by hostname without TLS inspection (domain-fronting caveat is in Anthropic's own docs) and the default sandbox read policy still allows reading ~/.ssh and ~/.aws/credentials; (5) an MCP-server-only gateway (no hooks) sees only calls addressed to its own tools, not Bash/Edit or other servers.

CODEX — gateway-ability grade: B-/C+ (partially governable; OpenAI's own docs say so). Codex now ships a Claude-Code-style hooks system (PreToolUse/PermissionRequest/PostToolUse etc., same permissionDecision + updatedInput JSON schema, exit-2 blocking, hash-based trust review via /hooks) — but the official docs explicitly scope PreToolUse to Bash, apply_patch file edits, and MCP tool calls, state it "doesn't intercept all shell calls yet, only the simple ones" (unified_exec interception incomplete), doesn't intercept web_search or other non-shell/non-MCP tools, and call it "a guardrail rather than a complete enforcement boundary." Compensating controls a gateway should drive via config: Starlark prefix rules (allow/prompt/forbidden, most-restrictive-wins) for commands escaping the sandbox; approval_policy (untrusted/on-request/on-failure/never) + sandbox_mode (read-only/workspace-write/danger-full-access) with network off by default in workspace-write; per-MCP-server enabled_tools/disabled_tools and per-tool approval_mode; tools.web_search = "disabled" to close the non-interceptable web-search path. Honest boundary list: (1) interception is documented-incomplete even locally; (2) Codex Cloud tasks execute in OpenAI-hosted environments launched from web/IDE/GitHub — outside any local gateway (whether repo-committed .codex hooks run there is undocumented); (3) --yolo / danger-full-access removes sandbox and approvals entirely; (4) all governance is user-editable config absent enterprise managed configuration.

Product implication: market the gateway as full pre-execution mediation for Claude Code's local sessions, and as "best-effort guardrail + config hardening" for Codex — disclosing per-agent the cloud-execution and self-disablement blind spots above.

### 角度：landscape-need

**小结**：The protective need is real and well-documented for 2025-2026, and the competitive landscape is already crowded on the enterprise/developer side - but thin on the specific niche our concept targets (cross-agent, consumer-grade, Touch ID ceremony, local-first audit).

PROTECTIVE-NEED EVIDENCE (strong, primary-sourced): Simon Willison's "lethal trifecta" (coined 16 June 2025) is the dominant plain-language framing: an agent that combines (1) access to private data, (2) exposure to untrusted content, and (3) ability to externally communicate can be tricked into exfiltrating data. This is not theoretical - 2025 produced multiple documented real-world incidents: the GitHub MCP prompt-injection exfiltration (Invariant Labs, May 2025), the WhatsApp MCP tool-poisoning data theft (Invariant Labs, April 2025), and the first confirmed MALICIOUS MCP server in the wild (postmark-mcp, Sept 2025, silently BCC'd every email to an attacker). Snyk's ToxicSkills audit (Feb 2026) found ~37% of agent skills carry at least one security flaw and confirmed live malicious skills. OWASP shipped both an updated LLM Top 10 (2025) and a dedicated Top 10 for Agentic Applications (Dec 2025). The MCP ecosystem is large and now Linux-Foundation-governed (>10,000 public servers; Anthropic donated MCP to the Agentic AI Foundation on 9 Dec 2025), so the attack surface is mainstream, not fringe.

COMPETITIVE LANDSCAPE (honest): The "MCP firewall / approval gateway / agent observability" space is ALREADY populated - Preloop, agentgateway, Lasso MCP Gateway, mcp-firewall, Pipelock - but these are overwhelmingly enterprise/team-oriented, self-hosted infrastructure (YAML/CEL policy, control planes). The closest consumer-grade, macOS-native, Touch-ID-gated, local-first comparable is Agent Secret - but it is scoped ONLY to secrets/credentials (1Password/Bitwarden references), not general tool-call/agent-action approval.

NOVELTY ASSESSMENT (sober): The general primitives (proxy interception, human-in-the-loop approval, audit logging, Touch ID gating) are all individually attempted/shipped. Genuinely less-occupied ground: (a) CONSUMER-grade rather than enterprise control-plane; (b) CROSS-AGENT general action approval (not secrets-only like Agent Secret, not single-framework); (c) Touch ID ceremony as the approval primitive for arbitrary agent actions; (d) local-first audit with no cloud dashboard. CRITICAL HONESTY CONSTRAINT (load-bearing, vendor-confirmed): a VOLUNTARY MCP/CLI gateway CANNOT see agent actions that bypass it - agents with bash/shell/code-execution can call APIs directly or drive headless browsers, "bypassing MCP servers entirely" (AWS Security, Apr 2026). Any honest disclosure must state the gateway sees only what routes through it; it is a consent/visibility layer for cooperating agents, not a containment boundary.
