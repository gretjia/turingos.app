## Scored dimensions (1–5)

### 1. boundary_wrappability — 3
- `src/lib.rs:16` (`pub mod state`) + `src/state/mod.rs:16` (`pub mod sequencer`) make every `pub` item in the file full crate-public API. The pub surface is wide: ~26 `*_accept_state_root` helpers (sequencer.rs:103–497), `Sequencer` + `new`/`new_at_logical_t` (5056, 5099), `submit`/`submit_agent_tx`/`emit_system_tx`/`run` (6587, 5180, 5359, 6595), plus test-leaning items — `try_apply_one` (6621, doc at 6617: "Production code uses run() instead"), `replace_q_for_test` (7101–7106, `#[cfg(debug_assertions)] pub`), `next_emit_id_peek` (5160), and the panicking `refine_rejection_class_via_attempt_telemetry` (867).
- Constructor leaks internals: `Sequencer::new` (5056–5067) takes 10 parameters of deep internal types (`Arc<RwLock<CasStore>>`, `Arc<Ed25519Keypair>`, `Arc<RwLock<dyn LedgerWriter>>`, `Arc<RwLock<RejectionEvidenceWriter>>`, `Arc<PredicateRegistry>`, `Arc<PinnedSystemPubkeys>` …) — a CLI/lib facade must construct and re-export six internal subsystems to instantiate one sequencer.
- Mitigations that prevent a lower score: heavy machinery is `pub(crate)` — `dispatch_transition` (1848), the domain consts (73, 118, 121 …), the `verify_fc3_*` context fns (1556–1812); and the accept-state-root helpers are deliberately single-semantic pub items so integration tests don't re-derive hash composition (doc 96–102: "the composing primitives stay pub(crate)"). Wrappable, but the facade cannot hide the internals without a re-export layer.

### 2. error_discipline — 4
- Result-threaded apply path with semantic, documented error enums: `ApplyError` (4882–4896) with explicit provenance rationale vs spec (4873–4880: "widens to Result<LedgerEntry, ApplyError> to preserve distinct error provenance"); `SubmitError` (4589–4610) and `EmitSystemError` (4789–4828) document each variant's trigger; `From` impls 4912–4931; `run()` separates ordinary transition rejections (logged, loop continues) from infra/integrity failures (fail-closed return) at 6602–6608.
- Deductions: (a) `pub fn refine_rejection_class_via_attempt_telemetry` panics on CAS error (`panic!("CAS integrity error during rejection-class refinement: {e}")`, 874) while production uses the `_checked` variant (6694) — a pub panicking API survives for one integration test (`tests/tb_18r_attempt_routes_to_l4_or_l4e.rs`). (b) All 26 `*_accept_state_root` helpers carry `.expect("TypedTx is canonical-encodable")` (84, 134, 145 … 497) where the in-`apply_one` encode path uses `map_err(... ApplyError::PayloadEncode)` (6933–6934) — two failure-mode regimes for the same operation. (c) In `refine_..._checked`, a poisoned CAS lock silently returns `Ok(base_class)` (919–921, 937–939), inconsistent with the function's own doc "propagates CAS integrity failures instead of silently degrading" (878–880). (d) `ApplyError::QStateLockPoisoned` is documented as "q.read()/q.write() lock poisoned" (4894–4895) but is also mapped for CAS (6659, 6906), rejection-writer (6700), and ledger-writer (7063–7065) lock poisoning — diagnostics mis-attribute the poisoned lock.

### 3. invariant_documentation — 5
- K1 dual-counter invariant written on the struct (4959–4962: "next_logical_t advances ONLY at commit time — rejected submissions never get a logical_t") and the v1.1 C-2 closure note in `apply_one` explains exactly why `fetch_add` was moved after commit success (6722–6731), with the commit-then-store sequence inline-commented at 7066–7068 ("commit succeeded → safe to advance counter").
- Inv 7 / no-advance-on-reject is stated at the rejection arm (6900–6902, 6925–6926: "No logical_t advance, no state_root advance, no ledger_root advance"); single-writer per (runtime_repo, run_id) at module doc line 9 and struct doc 4957; K3 head_t semantics at 4964–4970; append-only ledger discipline via the writer's "strict len + 1 invariant" cited at 5089–5092.
- Invariants are also asserted, not just narrated: tests carry invariant messages ("logical_t MUST NOT advance at submit", 7419–7423; "logical_t MUST NOT advance on rejected apply_one", 7452–7455), and debug-build invariant panics name the violated contract verbatim (962–966, 985–989).
- Only blemish: stale module doc lines 11–15 still claims "every per-kind transition returns TransitionError::NotYetImplemented" while the in-module test at 7380–7403 proves only the Reuse arm remains stubbed.

### 4. test_depth — 5
- 48 `#[test]`/`#[tokio::test]` functions in-module (7217–9592) plus integration coverage (`tests/tb_2_runtime_boundary.rs` — referenced from doc 97–99; `tests/tb_5_system_ingress_barrier.rs` — 8 `Sequencer::` references; `tests/tb_18r_attempt_routes_to_l4_or_l4e.rs`).
- Gold-standard exact expectations: `dispatch_transition_worktx_returns_state_root_via_domain_v1` (7656; comment 7648–7655) asserts `q_next.state_root_t` equals the exact `sha256(WORKTX_ACCEPT_DOMAIN_V1 ‖ prev ‖ worktx_canonical_hash(tx))` composition — "Locks the interim hash so any future change is loud."
- Adversarial/failure-path coverage: `run_fails_closed_on_cas_integrity_error_before_continuing_queue` (7556–7646) hand-forges a corrupt CAS sidecar (CID→wrong blob), then asserts the run loop returns `SequencerError::ApplyFailed(ApplyError::Cas(_))`, appends **zero** L4.E rows, and consumes no logical_t. `apply_one_rejected_path_uses_envelope_submit_id` (7465–7496) asserts exact L4.E row fields (submit_id=42, rejection_class mapping, parent_state_root carried in). Queue saturation and closed-receiver paths are tested (7775, 7824).
- Assertions are non-tautological — expected values are pinned constants or independently recomputed, with diagnostic messages on nearly every `assert_eq!`.

### 5. concurrency_safety — 4
- Single-writer contract documented at module doc line 9 and struct doc 4957; counters are `AtomicU64` SeqCst with an honest non-atomicity caveat and an upgrade path ("if multi-writer ever lands the AtomicU64 can be upgraded to a compare_exchange reservation pattern", 6728–6731). Submit-side ordering contract is explicit and test-locked: "fetch_add precedes try_send, so submit_id allocation order is NOT receiver arrival order … submit_id is always burned" (5338–5342).
- Lock sites observed acquire a single lock at a time (snapshot helpers 5480–5507; q snapshot 6742–6745), except the one multi-lock site — stage 9 `q.write` → `ledger_writer.write` (7061–7065) — and I found no opposite-order site (checked all `ledger_writer.read|write` / `self.q.read|write` hits; full-file exhaustiveness UNVERIFIED beyond those grep hits). The CAS stale-index read→write-reload→read retry dance is documented with its rationale (911–917, 6907–6913).
- Deductions: `run()` is async (6595) but `apply_one` does blocking `std::sync` locking plus ledger/git commit on the executor thread (7053–7073) — safe under the single-writer design but a facade embedding this in a shared tokio runtime can stall unrelated tasks; and the lock-poison silent fallback at 919–921 means a poisoned CAS lock changes evidence classification rather than failing closed.

### 6. dead_code_density — 5
- Zero `TODO`/`FIXME`/`XXX`/`allow(dead_code)` in 9592 lines (rg over the whole file); the only `#[allow]`s are two `clippy::too_many_arguments` on the constructors (5055, 5098).
- No commented-out code blocks found: the `// assert_*` grep hits (3429, 3505, 3723, 4005 …) are prose line-wraps naming invariant functions, not disabled code; the file's ~2240 comment lines are spec/charter citations. The only rot identified is the stale "Stub state" module doc (11–15) contradicted by the test at 7380–7403.

## Summary

src/state/sequencer.rs is an unusually well-disciplined 9.6k-line Class-4 surface: invariants (K1 dual counter, Inv-7 no-advance-on-reject, single-writer, post-commit logical_t store) are written down at the exact code sites and locked by high-quality tests, including a golden exact-hash state-root assertion (7656) and an adversarial corrupt-CAS fail-closed test (7556) — test depth and invariant documentation both score 5, and dead-code density is near zero (no TODO/FIXME/dead_code allows in the whole file). The weaker axes are portability-shaped rather than correctness-shaped: the crate-public surface is wide and constructor-leaky (10 internal-typed params at 5056; test-oriented pub items like try_apply_one and the debug-build replace_q_for_test), and error discipline, while Result-threaded with semantic enums, retains a pub panicking refine wrapper (874), 26 expect()-on-encode pub helpers, a silently-degrading poisoned-lock fallback (919-921), and an over-loaded QStateLockPoisoned variant. For the R1.9 port the headline items are the attention-level findings: the panicking pub wrapper, the lock-poison silent fallback in rejection-class refinement, and the debug-profile state-injection hole — none block wrapping, all deserve a facade-side decision before exposure.
